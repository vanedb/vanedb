stable public contract, runnable documentation and functional verification on
every advertised platform. C++ remains frozen reference code, with its defect

is accepted for this release; physical-device checks remain a follow-up, with
no physical-device success claim.

## Local performance and recall — September 7, 2026

Measurements use an Apple M4 Pro on macOS 26.6.2, AC power, and Homebrew Rust
1.98.0/LLVM 22.1.8. Both arms are built before interleaved A/B/A/B timing.
Cases request one second of warmup and two seconds of measurement; build/add
cases retain ten samples, other cases use twenty. Periodic process/load
recordings identify interference; they cannot exclude activity between samples
or establish freedom from GPU, kernel or frequency variation.

CPU comparisons use `9ed4343` versus `74d5c66`. The latter's CPU implementations
match `37512df`: the intervening runtime change affects optional Metal upload
only. Disk and flat-store rows from the full run, a focused index repeat, and
separate 128/768-dimensional Rust distance repeats show no regression beyond
observed variation. Distance deltas are +0.1% to +1.5%, within the approximate
3% practical noise floor. Rust disk open is +4.2% with 5.8% baseline spread;
that individual result remains inconclusive at this scale. Rust index search
is -3.1%, too close to the floor for a strong speed claim. The fixed small
flat-search case is -4.5%. Contaminated index/distance attempts were excluded;
only the identified clean repeats support these conclusions.

The CPU recall smoke passes at recall@10 of 0.700 for Rust and 0.689 for C++
over 100 uniform-random L2 queries against 10,000 × 128 vectors. Its incidental
timings are excluded. Synthetic recall does not predict embedding-corpus recall.

The first normal-data Metal comparison validated all three metrics at
4,096 × 128, k=10. Reused-buffer search improved about 31–32%, but the safety
changes made upload-plus-search about 60% slower. Commit `bced9f8` combines
finite and tiny-value classification in one portable, vectorized scan.
Focused L2 A/B/A/B timing of the changed paths measures:

| Comparison | Upload | Upload plus search |
|---|---:|---:|
| Previous safety candidate `74d5c66` → fused scan | 349.70 → 159.54 µs (-54.4%) | 565.92 → 363.61 µs (-35.7%) |
| Original `c322b19` → fused scan | 100.36 → 161.13 µs (+60.55%) | 360.95 → 365.60 µs (+1.29%) |

The safer upload retains a real upfront cost; reuse uploaded buffers across
queries. The +1.29% end-to-end delta is within the practical noise floor, not
proof of equivalence. Independent performance review accepts this tradeoff for
the tested warm, serial L2 workload. It does not establish cold-start latency,
scaling, concurrent throughput or performance on other devices/OS versions.
No competing process above 20% of one CPU core appeared in the retained
comparisons' periodic samples; earlier interfered runs are explicitly excluded.

Two pre-fusion tiny-value repeats match CPU distances and rankings, including
ties; their reused fallback scans are within about 1% of direct CPU scans.
Final-source normal/tiny correctness checks pass, and the reused fallback code
is unchanged. Final-source tiny-input upload timing is unmeasured; old absolute
fallback timings belong only to `74d5c66`.

Raw Criterion data, commands, source/executable hashes, exact sample identities,
load logs and exclusions are retained in `/private/tmp/vanedb-release-perf/`
(`assessment-74d5c66.json`) and `/private/tmp/vanedb-metal-perf/`
(`optimized-targeted-comparison.json` and
`original-optimized-targeted-comparison.json`). No CI timing is used as
