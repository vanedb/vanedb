Evidence for the frozen 0.2.0 release source. It replaces the September 27
draft, whose source `fbefa91` was superseded by three further release
candidates. **Nothing here authorizes a tag or publication.** That is a
separate, explicit maintainer decision.

## Performance

No dedicated-hardware result exists for this release. One interleaved run on
a developer Mac and an Android emulator failed the load screen; three runs
in all failed it on different macOS services. The numbers, the screen
outcome and their limits are in
[0.2.0-rc.4-evidence.md](0.2.0-rc.4-evidence.md). In summary:

- Against RC2, Rust graph search is about 1% slower, inside the roughly 3%
  local noise floor, in steps that had no flagged sample. Build time and
  the distance kernels did not move. The frozen C++ engine's search is 8.6%
  slower than its RC2 build, cause not isolated.
- Against the long-standing baseline `51cb2d8`, Rust `store_add` takes 0.57
  times as long, `disk_build` 0.84, `disk_open` 0.94; index build and search
  are flat. In the same run the Rust-to-C++ ratios were 0.80 for `store_add`
  and 1.02 for `disk_build`. Both are under the 1.1 target of RFC 0010, but
  that criterion asks for a dedicated machine and these steps carried
  flagged samples, so the result is indicative only.
- In the competitor harness vanedb searched faster than usearch and hnswlib
  at the same `ef` but at lower recall. At matched recall it is roughly 4%
  to 11% slower than usearch and still faster than hnswlib. Its build time
  uses `add_batch` and is not comparable with the serial builds beside it.

Maintainer decisions of 2026-11-11: the search cost is accepted, and 0.2.0
may release on this screened-and-flagged data with the disclosure above. The
dedicated-hardware slots in [bench/COMPARISON.md](../../bench/COMPARISON.md)
stay unclaimed, and no performance claim is made in the release notes.

The Linux x86-64 AVX2 tables were deferred past 0.2.0 by the amendment to
[RFC 0003](../rfcs/0003-competitor-benchmark-and-demo.md) accepted on
2026-11-10. No physical Android device was measured.

The September finding of a roughly 5% native search slowdown in a
fixed-graph probe was not reproduced as a separate experiment. The
interleaved runs since then show Rust `index_search` flat against the same
baseline.

## Known limits shipped with 0.2.0

- Graphs built with `M < 16` trade some narrow-beam recall for
  reachability; [docs/LIMITS.md](../LIMITS.md) has the measurements.
- A graph file written by an earlier release keeps its topology, including
  any stranded vectors, until `compact()` rebuilds it.
- Mobile evidence is simulator and emulator only.

## Sign-off reviews

Ten independent role reviews were run on 2026-11-11 against the first frozen
source `329d481` and these documents: CTO, AI product manager, senior
engineer, QA, technical program manager, analyst, SRE, DevOps, product
design and UX. Three approved and seven approved with conditions; none
rejected and none found a defect in the engine or bindings. The conditions
that concerned packaged files are the README corrections that produced S.
The rest were documentation corrections, applied in the pull request that
carries this file: the competitor and C++ interpretations in the RC4
evidence, the stranded-vector check and the `compact()` wording in
`docs/LIMITS.md`, the silent JavaScript rename in the notes, and amendments
to RFCs 0003 and 0010 recording the measurement decision.

The reviews were not repeated on S. S differs from what they reviewed only
in the corrections they asked for.

Left for follow-up, none blocking: after a load, a newly inserted node can
be left without a protected edge when the last 64 loaded nodes are all
full; `add_batch` raises `ValueError` and not the specific error classes;
several beginner-facing error messages omit the path or the cause; the
checklist boxes of RFC 0002 stage 1 are unticked pending a per-leg check.

## Held back on purpose

Seventeen Dependabot pull requests are open and deliberately unmerged.
Three of them change the root lockfile. Tags go on S, and the tag workflows
require only that S be an ancestor of `main`, so merging them afterwards
does not affect the release; merging them before tagging would.

The `crates-io`, `pypi` and `npm` environments were re-checked on
2026-11-11: each requires the maintainer as reviewer and restricts
deployment to its own tag pattern.

   with `capi_release.py verify` against `refs/tags/vanedb-crate-v0.2.0`;
   confirm npm `latest` is `0.2.0` (`next` stays on RC4) and that the
   GitHub release is not a prerelease and is marked latest.
4. If any registry fails: stop, keep the tags, record exactly which
   versions and files were accepted, and decide the next step with the
   maintainer. A used version number cannot be reused.
5. Close or move milestone issues #77 and #198, update the roadmap
   statuses, and merge the held dependency updates.
