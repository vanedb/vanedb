# VaneDB 0.2.0 — draft

**Unpublished, prepared candidate.** Rust, Python, C ABI and WebAssembly
package metadata target 0.2.0. The frozen C++ reference carries the same
version for cross-engine identity checks; its Python package is not published.
This draft describes the combined local candidate, not a release announcement
or sign-off.

At the September 25 checkpoint, protected main is `78d682c`: wheel
[PR #267](https://github.com/vanedb/vanedb/pull/267), C ABI
[PR #265](https://github.com/vanedb/vanedb/pull/265), persistence
[PR #286](https://github.com/vanedb/vanedb/pull/286) and filter
[PR #268](https://github.com/vanedb/vanedb/pull/268) have merged after green
current-head checks. The local candidate also incorporates prepared signing,
bulk disk writes and issue-automation corrections. Those remaining PRs and
this metadata PR still need their own current-main integration and green
checks. Local composition does not establish protected-main acceptance or
published availability.

## Prepared changes

- Per-query allow lists, deny lists and predicates restrict search results in
  Rust, Python, C and WebAssembly. Filtered graph search traverses excluded
  nodes and widens its beam when fewer than `k` results are found, up to the
  configured beam cap. Approximate recall is not guaranteed; tune the initial
  beam and cap against exact search on application data.
- Approximate indexes support byte serialization across bindings. JavaScript
  adds asynchronous `save`/`load` through IndexedDB in browsers or filesystem
  storage in Node; an unknown stored name returns `null`.
- Lookup misses return `Ok(None)` in Rust, `None` in Python and `undefined` in
  JavaScript. Rust callers replace `size()` with `len()` and `get_ef_search()`
  with `ef_search()`. JavaScript callers replace `ef_search` with `efSearch`.
  Python `Metric` is an `IntEnum`. The [changelog](../../CHANGELOG.md) contains
  the binding-specific migrations, including missing-ID removal errors.
- Internal ID hashing and write validation have changed. On little-endian
  hosts, disk saving writes the ID and vector payloads in bulk while
  preserving their existing wire bytes, validation and atomic-save behavior.
  Big-endian hosts retain explicit little-endian encoding. Dedicated hardware
  performance acceptance is still pending; this draft makes no speed claim.
- The [platform policy](../PLATFORMS.md) records support tiers and floors.
  Metal remains an experimental Rust distance-scan component; it accelerates
  no index. Mobile runtime evidence remains simulator/emulator based.

VNDB v1 disk files, VNDB v2 graph files and legacy readers remain in use.
There is no new persistence format in this version metadata change.

## C ABI migration

The prepared [stage 1 C ABI](../../vanedb-capi/README.md#using-the-abi) uses
ABI version 1. `vanedb_rs_store`, `vanedb_rs_index` and `vanedb_rs_disk` are
`uint64_t` handles, replacing pointers. Recompile consumers against the new
header and migrate every handle declaration and FFI binding:

- Drop the `*` from those three handle types. Use `VANEDB_RS_NULL_HANDLE` (0)
  instead of `NULL`, `PRIu64` instead of `%p`, and `uint64_t` instead of a
  generic `void *` slot used to hold a handle.
- In Python `ctypes`, declare handle arguments and results as `c_uint64`,
  not `c_void_p` or the default integer type.
- Compare `VANEDB_RS_ABI_VERSION` with `vanedb_rs_abi_version()` before calling
  other APIs. The generated header's `VANEDB_RS_VERSION` and runtime
  `vanedb_rs_version()` also expose the package version.

Never-issued, freed, wrong-kind or truncated handles report
`VANEDB_RS_INVALID_HANDLE` (16); freed IDs are not reused. Zero still reports
`VANEDB_RS_NULL_ARGUMENT`, and freeing zero remains a no-op. Keep mapped files
unmodified until the handle is freed **and all in-flight calls return**;
freeing a handle does not wait for those calls. See the
[C ABI guide](../../vanedb-capi/README.md) and [changelog](../../CHANGELOG.md)
for lifetime, error and migration details. The combined 0.2.0 header has been
regenerated locally; final distributed artifacts still require verification.

## Planned signed C distribution

The prepared [stage 5 signing workflow](RELEASING.md#signed-c-distribution-rfc-0002-stage-5)
targets five desktop archives: Linux x86-64/ARM64, macOS x86-64/ARM64 and
Windows x64. The complete set has 13 payloads and 13 Sigstore bundles:
five archives, five target-specific SBOMs, `CAPI-RELEASE.json`,
`CAPI-VERIFYING.md` and `SHA256SUMS`. This describes the intended 0.2.0
release contents; no 0.2.0 assets are claimed published here.

Follow the [signed-release verification instructions](../../vanedb-capi/README.md#signed-release-verification-020-onward).
Verify the exact `publish-capi.yml` certificate identity for
`refs/tags/vanedb-crate-v0.2.0`, the GitHub OIDC issuer
`https://token.actions.githubusercontent.com`, and the approved source-SHA
certificate claim before trusting the checksums and inventory. A branch
rehearsal signature does not satisfy the release tag identity. The final
release notes and `CAPI-VERIFYING.md` must provide the full verification
commands with the actual approved source SHA; it is not assigned in this
draft. Archive compatibility metadata records binary requirements and tested
hosts, not proof of runtime support on the oldest OS. RFC 0002
[stages 2–4](../rfcs/0002-c-abi-distribution.md), including Apple/Android
packaging and other native ecosystems, remain outside this release.

## Remaining release gates

- **Performance:** dedicated write-path and competitor acceptance remain
  open. September 24 diagnostics on an unreserved Mac measured `disk_build`
  at 1.148× Rust/C++, above the [RFC 0010](../rfcs/0010-write-path-gaps.md)
  1.1× target. A September 25 disk-only, six-pass diagnostic observed a
  1.058× ratio of the median Rust and C++ build-time estimates with the
  bulk-write candidate, but one pass was 1.115× and the host was unreserved.
  Neither diagnostic establishes a reliable
  speedup or final-candidate acceptance. Rerun all required write and search
  rows on a quiet, reserved Mac and investigate if a gap is confirmed; an
  amendment requires dedicated measurements.
  The [RFC 0003](../rfcs/0003-competitor-benchmark-and-demo.md#hardware)
  Linux x86-64 AVX2 and Android ARM64 competitor arms remain missing. Android
  may use a physical ARM64 device or an explicitly labelled ARM64 emulator.
- **Capacity:** [#210](https://github.com/vanedb/vanedb/issues/210) is closed
  as completed research for 0.2.0. The full physical-device capacity matrix
  is tracked separately in [#285](https://github.com/vanedb/vanedb/issues/285),
  milestone 0.4.0. This agreed split waives no current-engine benchmark gate.
- **Demo and launch:** demo main
  [`5f98bfec`](https://github.com/vanedb/obsidian-vane-search/commit/5f98bfec5fc16dcef171bcde7dee4f669bbe55f9)
  builds the accepted 222 KB bundle with SHA-256
  `db6f18a706e3650470adcd4961dc1ba62d7011775bd4e60e4438f1b1dfd78775`.
  The [real Obsidian/Ollama walkthrough](https://github.com/vanedb/obsidian-vane-search/blob/5f98bfec5fc16dcef171bcde7dee4f669bbe55f9/docs/releases/0.2.0-desktop-acceptance.md)
  passed, including edits, deletion, failed rebuild recovery and restart.
  Official demo 0.2.0 publication awaits user approval. This demo embeds
  engine 0.1.1; its acceptance does not establish engine 0.2.0 desktop
  acceptance. Launch work remains tracked in
  [#242](https://github.com/vanedb/vanedb/issues/242) and
  [#253](https://github.com/vanedb/vanedb/issues/253).
- **macOS Python build environment:** on the local macOS 27 host, candidate
  builds using SDK 27 fail to import with a Mach-O LINKEDIT string-pool error.
  The pre-bulk source fails under the same build tuple, so reverting bulk
  writes is not a demonstrated remedy. Using SDK 26.5 with the same Rust
  1.94.1, Maturin 1.15.0 and linker produces a candidate wheel that passes
  all 240 installed Python tests and 15 additional disk-format cases. This
  control does not repair SDK 27 or validate the full wheel matrix. Install
  and test the unmodified final rehearsal's macOS wheel on this host, record
  its SDK/toolchain, and resolve any failure before accepting that artifact.
- **Final candidate:** merge prerequisites through current-base protected CI,
  then run full platform CI and publication-disabled crate/Python/npm/C
  rehearsals on the actual final-main candidate. Verify installed/extracted
  artifacts with exact source SHAs and checksums, reconcile findings and
  obtain unanimous independent role reviews. Historical rehearsals and
  local composition proofs do not replace those checks. Record fresh
  evidence before assigning a release date or requesting engine publication.
