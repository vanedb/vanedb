# VaneDB 0.2.0

Rust, Python, C ABI and WebAssembly packages are versioned 0.2.0. The frozen
C++ reference carries the same version for cross-engine identity checks; its
Python package is not published. Whether 0.2.0 is published is recorded on
the registries and the GitHub release, not by this file.

```sh
cargo add vanedb
python -m pip install vanedb
npm install @vanedb/wasm
```

Python requires 3.11 or newer. Wheels cover CPython 3.11 to 3.14 on Linux
x86-64 and ARM64 (glibc and musl), macOS x86-64 and ARM64 and Windows x64.

## Changes since 0.1.1

- Per-query allow lists, deny lists and predicates restrict search results in
  Rust, Python, C and WebAssembly. Filtered graph search traverses excluded
  nodes and widens its beam when fewer than `k` results are found, up to the
  configured beam cap. Approximate recall is not guaranteed; tune the initial
  beam and cap against exact search on application data.
- Approximate indexes support byte serialization across bindings. JavaScript
  adds asynchronous `save`/`load` through IndexedDB in browsers or filesystem
  storage in Node; an unknown stored name returns `null`.
- Lookup misses return `Ok(None)` in Rust, `None` in Python and `undefined` in
  JavaScript. Rust callers replace `size()` with `len()` and `get_ef_search()`
  with `ef_search()`. JavaScript callers replace `ef_search` with `efSearch`; the old name is not
  an error in plain JavaScript, so an assignment to `index.ef_search` or an
  `ef_search` option key is silently ignored. Search the code for it.
  Python `Metric` is an `IntEnum`. The [changelog](../../CHANGELOG.md) contains
  the binding-specific migrations, including missing-ID removal errors.
- Internal ID hashing and write validation have changed. On little-endian
  hosts, disk saving writes the ID and vector payloads in bulk while
  preserving their existing wire bytes, validation and atomic-save behavior.
  Big-endian hosts retain explicit little-endian encoding. No speed claim is
  made for this release: no measurement passed the dedicated-hardware screen.
- The [platform policy](../PLATFORMS.md) records support tiers and floors.
  Metal remains an experimental Rust distance-scan component; it accelerates
  no index. Mobile runtime evidence remains simulator/emulator based.

VNDB v1 disk files, VNDB v2 graph files and legacy readers remain in use.
0.2.0 adds no persistence format.

## C ABI migration

The [stage 1 C ABI](../../vanedb-capi/README.md#using-the-abi) uses
ABI version 1. `vanedb_rs_store`, `vanedb_rs_index` and `vanedb_rs_disk` are
`uint64_t` handles, replacing pointers. Recompile consumers against the new
header and migrate every handle declaration and FFI binding:

- Drop the `*` from those three handle types. Use `VANEDB_RS_NULL_HANDLE` (0)
  instead of `NULL`, `PRIu64` instead of `%p`, and `uint64_t` instead of a
  generic `void *` slot used to hold a handle.
- In Python `ctypes`, declare handle arguments and results as `c_uint64`,
  not `c_void_p` or the default integer type.
- Compare `VANEDB_RS_ABI_VERSION` with `vanedb_rs_abi_version()` before calling
  other APIs. The generated header's `VANEDB_RS_VERSION` and runtime
  `vanedb_rs_version()` also expose the package version.
- Recompile. A 0.1.1 binary started against the 0.2.0 library without
  recompiling is not refused by the loader and reports no error, and its
  behaviour is unspecified: the libraries
  carry no versioned link identity, and the handle change is invisible at the
  calling convention. Swapping the shared library in place is neither
  detected nor supported (#303).

Never-issued, freed, wrong-kind or truncated handles report
`VANEDB_RS_INVALID_HANDLE` (16); freed IDs are not reused. Zero still reports
`VANEDB_RS_NULL_ARGUMENT`, and freeing zero remains a no-op. Keep mapped files
unmodified until the handle is freed **and all in-flight calls return**;
freeing a handle does not wait for those calls. See the
[C ABI guide](../../vanedb-capi/README.md) and [changelog](../../CHANGELOG.md)
for lifetime, error and migration details.

## Signed C distribution

The [stage 5 signing workflow](RELEASING.md#signed-c-distribution-rfc-0002-stage-5)
produces five desktop archives: Linux x86-64/ARM64, macOS x86-64/ARM64 and
Windows x64. The complete set has 13 payloads and 13 Sigstore bundles:
five archives, five target-specific SBOMs, `CAPI-RELEASE.json`,
`CAPI-VERIFYING.md` and `SHA256SUMS`, attached to the
`vanedb-crate-v0.2.0` GitHub release.

Follow the [signed-release verification instructions](../../vanedb-capi/README.md#signed-release-verification-020-onward).
Verify the exact `publish-capi.yml` certificate identity for
`refs/tags/vanedb-crate-v0.2.0`, the GitHub OIDC issuer
`https://token.actions.githubusercontent.com`, and the approved source-SHA
certificate claim before trusting the checksums and inventory. A branch
rehearsal signature does not satisfy the release tag identity. The source
commit is `ebccc0a44132eafecc880d9e9fff70c16e742767`; `CAPI-VERIFYING.md` in
the asset set gives the full commands. Archive compatibility metadata records binary requirements and tested
hosts, not proof of runtime support on the oldest OS. RFC 0002
[stages 2–4](../rfcs/0002-c-abi-distribution.md), including Apple/Android
packaging and other native ecosystems, remain outside this release.

## Fixed during the release candidates

Four candidates preceded this release; the [changelog](../../CHANGELOG.md)
lists every change. The ones a 0.1.1 or candidate user is most likely to
meet:

- **Every stored vector stays reachable, which is not the same as
  returned.** Pruning an overflowing neighbour
  list could drop the last edge to a node, so under DOT, and under cosine on
  tightly clustered data, live vectors were returned by no search (#299).
  Layer 0 now keeps a spanning tree that pruning never cuts. Graphs built by
  0.2.0 differ from those built by 0.1.1 or the first two candidates for the
  same input and seed. A vector no neighbour kept is chained to the one
  stored before it: it is on a path, but only a wide beam returns it.
- **WebAssembly predicates that return a Promise or a generator now throw
  `TypeError`.** Both are always truthy, so an `async` predicate had matched
  every stored id.
- The defects found in RC1 testing are fixed; see the RC2 section of the
  changelog.

## Known limits

- Approximate search does not guarantee recall, filtered or not. Tune
  `ef_search`, and for filtered search the beam cap, against exact search on
  your own data. The measured figures for one embedding fixture are in the
  [filtered-search validation](0.2.0-filtered-search-validation.md).
- Graphs built with `M < 16` trade narrow-beam recall for reachability. On
  Gaussian L2 data recall is up to 4.5 points below RC2 at `M = 4`, and with
  DOT over very uneven norms most nodes hang off their predecessor at any
  `M`. At the default `M = 16` the measured difference is within 0.6 points.
  [docs/LIMITS.md](../LIMITS.md) has the measurements.
- A graph file written by an earlier release loads with the topology it was
  saved with, including any vectors that release stranded. Nothing reports
  this on load. [docs/LIMITS.md](../LIMITS.md#graph-reachability-and-exhaustive-queries)
  describes how to check a file, and `compact()` rebuilds it at the cost of a
  full build.
- No performance claim accompanies this release. One interleaved run on a
  developer Mac and an Android emulator is recorded, with its failed load
  screen, in the [RC4 evidence](0.2.0-rc.4-evidence.md). There are no Linux
  x86-64 AVX2 tables ([RFC 0003](../rfcs/0003-competitor-benchmark-and-demo.md)
  amendment) and no physical mobile-device results.
- The full physical-device capacity matrix is tracked in
  [#285](https://github.com/vanedb/vanedb/issues/285), milestone 0.4.0.
- RFC 0002 [stages 2 to 4](../rfcs/0002-c-abi-distribution.md), including
  Apple and Android packaging, are outside this release.
