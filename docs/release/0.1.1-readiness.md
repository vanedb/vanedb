# 0.1.1 release readiness

Status: **released**. Verified at `74235d7`, tagged at `d1553dd`, and
published to crates.io, PyPI and npm on 2026-09-10.

**What 0.1.1 publishes.** Four artifacts: the `vanedb` crate on crates.io, the
`vanedb` package on PyPI, `@vanedb/wasm` on npm, and the C ABI archives
attached to a GitHub release.

**Three of the four have shipped.** crates.io, PyPI and npm carry 0.1.1, each
verified against the artifact its own tagged run built and against the digests
in [`0.1.1-published.sha256`](0.1.1-published.sha256). The **C ABI archives have
not**: `RELEASING.md` calls for attaching them, with their runtime compatibility
metadata and the two wasm tarballs, to a GitHub release, and no release exists
for `vanedb-crate-v0.1.1`. Nothing published is wrong; one distribution channel
is simply not open yet, which is why the published manifest lists 31 files where
the build manifest lists 36. The five archives are in the CI run for `d1553dd`
and can be attached without rebuilding anything.

The supplementary `vanedb-cpp` C++ package is version-stamped 0.1.1 because
`release_identity` requires every site to agree, and is **not published
anywhere** — it is reference code and the second arm of the benchmark
comparison. CI builds and tests it; no workflow uploads it.
Rust, Python, C and WebAssembly use **0.1.1**. PR #184 includes #185's Wasm
`upsert` and per-query beam width, and reconciles #186's C++ pickle fix.

The [artifact manifest](0.1.1-artifacts.sha256) covers the **36 distributions
that publish**: 28 wheels, one sdist, one crate, five C archives and the npm
tarball. Every path carries its source commit as a prefix, so a filename cannot
stand for two different artifacts. Each hash was checked against the sidecar
`.sha256` files and `SHA256SUMS` that CI published beside the archives, so the
manifest attests to the bytes CI produced rather than to a local rebuild.

**It cannot validate a published file, and is not meant to.** Publishing builds
at the tag commit, which is necessarily a later commit than the one a
pre-publication rehearsal ran at, and `cargo package` embeds that commit in
`.cargo_vcs_info.json`. The published crate and the rehearsal crate therefore
differ in exactly that one file and are byte-identical everywhere else —
checked, after the difference in hashes suggested a defect that was not there.
This manifest attests that the pipeline and the source were sound at the
verified commit. To validate a file that shipped, use
[`0.1.1-published.sha256`](0.1.1-published.sha256), which records the digests
the registries themselves publish; each was also confirmed against an
independent download and against the artifact its own tagged run produced.

The earlier count of 38 also counted the two intermediate wasm build
directories, which are inputs to the npm tarball rather than distributions.

The old 0.1.0 manifest is historical but is **not** disjoint from this one: its
first line records `4aa60c8/npm/vanedb-wasm-0.1.1.tgz`, from the abandoned plan
that proposed npm 0.1.1 alongside crates.io and PyPI 0.1.0. Two different
byte-sets therefore carry the same filename across the two manifests, for a
version npm will never allow to be re-uploaded. The 0.1.0 entry is superseded
and must not be published. Identify an artifact by its source revision
and SHA-256, not its filename.

## Platform and compatibility scope

Runtime coverage includes Linux x86-64/ARM64, macOS Intel/ARM64 and Windows
x64. Python wheels additionally cover musl Linux. C archives record glibc
requirements and macOS deployment targets; those are binary requirements,
not proof of runtime behavior on the oldest compatible OS.

Mobile acceptance is simulator/emulator based: iOS ARM64, Android x86-64,
and Android ARM64 with 16 KiB pages. The recorded ARM64 runtime result used
the CI-built binary from `30c1824`. Its native Rust/C implementation, third-party
dependencies and Android build inputs are unchanged at `9b53115`; this supports
carrying forward that runtime result, not claiming a new binary was executed.
Current CI must still pass the mobile builds and acceptance jobs. Physical-device
and oldest-OS runtime acceptance remain follow-ups; no physical iPhone/Android
test is claimed.

Metal is an explicit Rust compute API; it does not automatically accelerate
indexes. CUDA remains a required [post-release follow-up](../ROADMAP.md).
Earlier dedicated-hardware performance evidence applies only to unchanged
implementations; CI timings are not performance evidence. The release delta
keeps third-party dependency versions unchanged.

VNDB v1 disk and VNDB v2 graph formats retain cross-engine conformance and
legacy readers. During 0.x, minor releases may change APIs/formats; existing
format identifiers are never reinterpreted. See the [release notes](0.1.1-notes.md).

## Publication handoff

This sign-off authorised no tags, uploads or merges; those followed it, under
[RELEASING.md](RELEASING.md), with each publish job gated on a protected
environment the maintainer approved.

The rehearsed artifacts carry their own recorded source and checksums, and a
later rebuild did replace them — that is what publishing is. `cargo package`
embeds the tag commit, so the published crate cannot hash the same as one built
at an earlier commit, and checking that it did was a mistake made once and
corrected. Validate a shipped file against
[`0.1.1-published.sha256`](0.1.1-published.sha256) and the registry's own
digest, not against the rehearsal manifest.

All three trusted publishers executed successfully for rc.2. npm 0.1.0 was
already consumed by a manual bootstrap; using 0.1.1 for every registry removes
the earlier version split. TestPyPI 0.1.0 and 0.1.0rc1 contain partial historical
uploads. The 0.1.1 rehearsals above kept publication disabled.
