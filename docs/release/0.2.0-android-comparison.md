# Android ARM64 comparison evidence — September 27, 2026

**Both full datasets completed and passed the unchanged renderer checks.
Host-load qualification remains unresolved; this is not a performance gate
PASS or a physical-device result.** The original harness JSON is preserved
below, including its limitations and all engine rows.

## Source, environment and method

Frozen source S: `fbefa9197960c0398f0dc4762c3cd3ea726d6d6a`, tree
`a8beeee559081b0f548cca9afb0a4f6d904a1ac1`. Rust 1.94.1 built the unchanged
comparison harness with its lockfile, offline, for `aarch64-linux-android`.
NDK 26.1.10909125 supplied the API 24 compiler and C++ shared runtime.

The AVD was `vanedb_020_full_api35_arm64`: API 35 default ARM64 image
revision 2, Android emulator 37.1.11, four virtual CPUs, 8 GiB RAM and a
16 GiB data partition, using macOS 27 Hypervisor.Framework on the reserved
Apple Silicon host. The guest reported ARM64 and 4 KiB pages. The C++ runtime
has 4 KiB LOAD alignment; this run establishes no 16 KiB compatibility.

The binary, runtime, fixture, checksum file and metadata were hashed on the
guest before measurement and matched the retained build/source records.
Android has no checkout, so the harness reports `commit: "unknown"`; that
field is preserved. The external S-to-binary hash record supplies provenance.

Both metrics use the pinned 100,000 × 768 fixture, all 1,000 queries, k=10,
M=16, ef_construction=200, seed=42, and ef=16/32/50/100. Four rounds
interleave the engines in each metric. Cosine ran 13:33–14:33 UTC; L2 ran
14:34–15:32 UTC on September 27. Cosine includes five engines and omits
sqlite-vec, which lacks a native cosine vec0 metric; L2 includes all six.

USearch and hnsw_rs do not expose construction seeds. instant-distance fixes
M=32 and emits one ef=50 row. VaneDB builds with add_batch, not sequential
insertion. sqlite-vec is brute-force and its build includes database ingest.
These are not identical implementation workloads or matched-recall timings.
The JSON preserves each engine's notes, save support and deletion status.

## Validation and measurement limits

Both commands exited successfully. All expected engines and four rounds are
recorded, all supported delete checks passed, and both reports passed the
unchanged S render-policy checks. The completion checker confirmed output
hashes and shut down only this task's AVD.

The user reserved the Mac and preflight required three quiet samples before
each metric. All 236 measured-phase power samples reported AC. However,
**13 of 236 host samples exceeded the declared background-load screen**:
9/121 during cosine and 4/115 during L2. The screen flags any non-emulator
process above 50% CPU or their aggregate above 150%. It excludes the emulator,
adb and controller-related processes, so guest-internal background work is
not isolated. Sampling is not continuous observation. No thermal warning was
recorded; that does not establish a contention-free host.

The JSON's `dedicated_attested: true` records the user reservation. It does
not override these observed load flags. Renderer PASS validates report policy
and completeness, not the absence of interference. VaneDB cosine latency
spread is about 20–24% across ef values; L2 spread is about 4–6%. Do not infer
a general speed advantage, compare the emulator directly with physical
Android devices, or close the dedicated-performance gate from these data.

The retained harness JSON contains aggregate medians/spreads and a round
count, **not individual round timing records**. Original process logs confirm
round progression but cannot reconstruct those missing measurements. No
per-round values have been invented. RFC 0003 specifies interleaved runs,
medians and inter-pass spread; this appendix introduces no new requirement
to retain individual samples. Their absence limits independent recomputation
of the reported aggregates.
