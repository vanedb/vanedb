# VaneDB 1.0.0 — draft release notes

Unreleased. Package metadata is prepared for 1.0.0; publication still depends
on the [readiness requirements](1.0.0-readiness.md). Final candidate verification,
registry availability and publication approval must be settled
before these notes become a release announcement.

VaneDB searches embeddings inside your application without a database server.
Supply your own vectors and choose exact in-memory search, an approximate graph
for faster queries, or exact search over a read-only memory-mapped file.
All three use squared L2, cosine distance, or negative dot product, with
unsigned 64-bit IDs and finite vectors of a fixed dimension.

## What is included

- The Rust engine and Python bindings provide Flat, Approx and Disk indexes.
  Approximate indexes support batch insertion, deletion, replacement and
  compaction. Tune `ef_search` against exact search on your own data.
- Rust callers can pass `SearchParams` to `search_with` to choose a graph query's
  beam width without changing the index's defaults for other callers.
- The C ABI provides Flat, Approx and Disk indexes with generated ownership and
  buffer documentation. Each graph query can choose its own search beam width.
- Node.js and browser WebAssembly packages provide Flat and Approx indexes,
  batch insertion and deletion. IDs use JavaScript `bigint` values.
- Native C archives include libraries, the header, runnable CMake examples and
  the license. Node and browser packages are separate artifacts.
- GPU support is limited to the existing macOS Metal feature. CUDA is excluded
  from 1.0.0 and is a required, high-priority [roadmap follow-up](../ROADMAP.md).
  No delivery version or date has been assigned.

Mobile acceptance for 1.0.0 uses iOS simulators and Android emulators, including
Android ARM64 with 16 KiB pages. Physical-device runs remain a follow-up; these
notes make no claim of successful iPhone or Android device verification.

See the [Rust](../../vanedb/README.md), [Python](../../vanedb-py/README.md),
[C](../../vanedb-capi/README.md) and [JavaScript](../../vanedb-wasm/README.md)
guides for source builds and examples. Registry installation instructions and
release-asset links will be added after publication is verified.

## Moving from development versions

Approximate indexes now write shared VNDB v2 graph files. Rust and the frozen
C++ reference engine can exchange those files while preserving vectors, graph
links, IDs and deleted slots. Their subsequent insertions can produce different
graphs because the engines use different random generators.

Load a legacy graph in its original engine and save to a new path to migrate.
Rust retains its legacy v1/v2 readers; C++ retains its legacy v1/v2/v3 readers.
Keep the original file and source vectors until the migrated index is verified.
Older readers cannot open VNDB v2. The existing VNDB v1 disk format is unchanged.
The Rust engine in VaneDB 1.x will continue to read valid VNDB v1 disk and VNDB
v2 graph files written by VaneDB 1.0.0, within documented resource limits.
Future insertions need not reproduce identical graph topology.

This unreleased candidate also changes several development APIs:

- Replace Rust `search_with_ef` calls with `search_with` and
  `SearchParams::new().ef_search(...)`.
- `SearchResult` is non-exhaustive and remains `Clone`. Construct it with
  `SearchResult::new(id, distance)` and include `..` when destructuring it.
- Rust disk lookup returns `Cow<'_, [f32]>`; borrow its slice with `as_ref()` or
  use `into_owned()` when an owned vector is needed.
- Rust `DiskIndex::open` is now unsafe: callers must ensure that the underlying
  file cannot be modified or truncated from before opening through the mapping's
  entire lifetime. Python and C consumers have the same file-lifetime obligation.
- Python negative or out-of-range integer sizes and seeds raise `ValueError`.
- Disk loaders reject nonzero reserved VNDB v1 header bytes. Existing writers
  already write zero there; the file format itself has not changed.

Keep mapped disk files immutable until all indexes using them are released.
Read-only mappings cannot stop another process from modifying the file, which
can corrupt results or crash the application. Write updates to a separate file
and atomically replace the path where supported; existing mappings retain the
original file, and newly opened indexes read the replacement.

Approximate search can miss true neighbors. Deleted or replaced graph entries
retain storage until compaction. Building a disk index buffers vectors in memory
before writing its mapped-search file. WebAssembly does not expose persistence,
disk mapping or upsert. It does expose remove, tombstones and compact on
`ApproxIndex`, and reads stored vectors back with get/get_vector. The C++
engine is frozen reference code and has a different API and feature set.
