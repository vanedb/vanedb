# Filtered-search validation — 2026-09-20

PR #214 implements RFC 0004 for the upcoming 0.2.0 release. This records
validation of source commit `d86877433e8af4eca1ab60985ced12a7d681cfe7`, after
integrating main at `4ace7d6e021b2290b144c2de46f5373cb733f706`.

## Review findings resolved

- An empty C allow list previously selected an unfiltered search. Pointer
  presence now selects the mode, and conflicting modes and invalid pointer/
  length pairs fail without modifying result buffers.
- Python and JavaScript callback failures previously became rejected IDs,
  silently returning partial results. The original exception now propagates,
  and no more user callbacks run after the first failure.
- Python predicate search held the GIL while waiting for core locks. It now
  releases the GIL and reacquires it only while running Python code.
- Generated TypeScript declarations made new options mandatory. They are
  optional again, preserving existing omitted and numeric arguments.
- Beam arithmetic could overflow. Widths now saturate and are capped to the
  number of stored slots.
- Filtering controlled graph traversal, making selective searches scan the
  reachable graph and rendering widening ineffective. Separate routing and
  accepted-result heaps preserve the bounded routing beam. Compile-time
  specialization omits the added routing checks, predicate checks and visit
  counter from ordinary searches and graph construction.
- A predicate searching another graph panicked on the shared visited buffer.
  Nested searches now use separate scratch storage.
- WASM accepted conflicting filters and malformed options. It now validates
  modes, arrays, lossless IDs and numeric beam settings consistently.

Predicates must be stable for a query and must not access the same index:
they run under its read lock. They may consult external metadata or search a
different index. Callback failures discard partial results. These are public
contracts, documented in core docs, Python help, generated TypeScript and
binding READMEs.

## Recall on real embeddings

The pinned RFC 0003 fixture contains 100,000 BeIR/nq document embeddings and
1,000 queries from `nomic-ai/nomic-embed-text-v1.5`, 768 dimensions. SHA-256:
`4676911521f13dc6592d102cf3b4fcace85c6b62b3011e9bd57557dfc9c01f2d`.
All documents and queries were used. Cosine distance, `k=10`, `M=16`,
`ef_construction=200`, seed 42; allowed sets select every 2nd, 10th or 100th
fixture ID and are sorted before searching. Recall is measured against exact
filtered search on the same allowed set, not against unfiltered neighbors.

| Selectivity | Initial beam | Cap | Recall@10 | Queries returning ten results |
|---|---:|---:|---:|---:|
| 50% | 50 | 200 | 97.37% | 100% |
| 10% | 50 | 200 | 85.56% | 100% |
| 1% | 50 | 200 | 51.50% [^widening] | 99.0% [^widening] |
| 50% | 50 | 1600 | 97.37% | 100% |
| 10% | 50 | 1600 | 85.56% | 100% |
| 1% | 50 | 1600 | 51.80% [^widening] | 100% [^widening] |
| 50% | 1000 | 4000 | 99.99% | 100% |
| 10% | 1000 | 4000 | 99.82% | 100% |
| 1% | 1000 | 4000 | 96.19% | 100% |

Raw results: [initial beam 50](0.2.0-filtered-recall.json) and
[initial beam 1000](0.2.0-filtered-recall-tuned.json).

[^widening]: Re-measured on 2026-09-20 after the widening follow-up (see
    below) with the same pinned fixture, seed 42, `k=10`, `M=16`,
    `ef_construction=200` and the branch's default settings; the other rows
    reproduced to the digit in the same run, which is what makes the
    replacement comparable. Before the fix these two rows read 35.54% / 30.8%
    and 51.66% / 99.5%. Recall is a deterministic count, so the machine does
    not matter; no timings were taken from it.

The default cap is a work/recall tradeoff, not a recall guarantee. Increasing
only the cap does not improve queries that already return `k` matches because
widening stops at that point. Raise the initial beam too, or choose exact
search when missing matching neighbors is unacceptable. These results describe
this dataset and filter distribution; clustered application metadata can differ.

## Follow-up: widening at default settings

A post-merge review found that the widening loop compared the number of
nodes a pass visited against `max_ef_search`. One `ef_search = 50` pass on an
`M = 16` graph visits far more than 4 x 50 nodes, so at default settings the
search never ran a second pass and a selective filter returned fewer than `k`
with no signal: the 1% row above measured 30.8% of queries returning ten
results. The cap now bounds beam width only, as RFC 0004 and the READMEs
state, and a pass that has already scored every stored slot ends widening
early. Regression tests pin the behaviour on a 10k-vector index: a 1% allow
list returns `k` for every query at default settings (32 of 100 before), and
a reject-all predicate visits more than twice a single pass's nodes (4,504
versus 833 on the test's seed). The 1% rows above were re-measured with the
fix; the wider default work is a second and third pass only for queries
whose first pass found fewer than `k` matches.

## Unfiltered performance

Baseline `4ace7d6` and candidate `d868774` ran A-B-A-B-A-B on a physical
Apple M4 Pro Mac (14 cores, 48 GiB RAM, macOS 26.6.2, Rust 1.98.1).
Both revisions were built before measurement. No concurrent agent builds,
tests or recall runs were active during timing. macOS background activity was
present; the measured round-to-round spreads below are retained rather than
claiming tighter precision. These are local regression measurements, not
cross-platform latency claims.

The existing C ABI benchmarks use 128 dimensions, `k=10`, and 32 distinct
queries per timed sweep. Flat search covers 1,000 and 10,000 vectors; graph
and disk search cover 10,000. Graph parameters are `M=16`,
`ef_construction=200`, `ef_search=50`, seed 7. Times are the median of the
three reported per-sweep estimates for each revision.

| Operation | Baseline | Candidate | Change | Baseline spread | Candidate spread |
|---|---:|---:|---:|---:|---:|
| Disk search | 2.49390 ms | 2.50782 ms | +0.56% | 1.88% | 0.39% |
| Graph search | 923.35 µs | 932.16 µs | +0.95% | 1.02% | 6.75% |
| Flat search, 1k | 281.48 µs | 279.89 µs | -0.57% | 0.42% | 2.09% |
| Flat search, 10k | 2.43345 ms | 2.44421 ms | +0.44% | 1.70% | 0.93% |

All median changes are below 1%, within the project's 3% noise floor.
The existing `abtest` classifier reports every row as noise: no detected
unfiltered regression. [All six rounds](0.2.0-filtered-search-bench.json)
retain Criterion's individual mean, median and slope estimates in nanoseconds.
The table uses slope estimates, as does Criterion's displayed `time` estimate
for these benchmarks.

Earlier runs of `926a43f` were inconclusive (graph deltas of +4.5% and +13.5%
with large spreads). They were not accepted as evidence of unchanged speed.
The subsequent specialization removes filter-related routing work from the
unfiltered loop; the table above is the measured final implementation.

Reproduce from the repository root:

```sh
cargo run --release --manifest-path bench/Cargo.toml --bin abtest -- \
  --a 4ace7d6e021b2290b144c2de46f5373cb733f706 \
  --b d86877433e8af4eca1ab60985ced12a7d681cfe7 \
  --bench store --bench index --bench disk --rounds 3 --keep -- \
  'search.*/rs$' --sample-size 50 --warm-up-time 3 --measurement-time 8
```
