## Method and hardware

Physical MacBook Pro Mac16,8, Apple M4 Pro, 14 cores (10P/4E), 48 GiB RAM,
macOS 27.2 build 26B123, native ARM64, `kern.hv_vmm_present=0`. This meets the
Apple Silicon hardware class. It cannot supply native Linux x86-64 AVX2
results; no translated binary or ARM VM is substituted for that class.

Rust/cargo 1.94.1 was explicitly selected for both arms; LLVM 21.1.8,
Apple clang 21.0.0, CMake 4.4.5. All builds, harness tests and smoke validation
finished on November 1, before the campaigns. No task-owned build or test ran
concurrently with measurements. Campaigns ran sequentially on AC with
`caffeinate`. The unchanged repository shared-runner check ran before each
campaign; its success is not a substitute for load evidence.

Each native target required three consecutive quiet five-second samples:
no background process above 50% CPU and aggregate background CPU at most
150%, using `ps`'s per-core scale. Samples continued during the entire target
process, including setup and warmup. Only the controller, sampler and active
benchmark process tree were excluded. Thus a flag does not locate a specific
Criterion timed interval, but conservatively disqualifies that campaign.
Samples cannot prove continuous isolation between observations.

The user-owned Spotlight indexer was temporarily suspended with SIGSTOP;
a guardian checked process identity and resumed it with SIGCONT when each
controller exited. It was not omitted from load accounting. User applications
and system security scans were not stopped or excluded. XProtect scans caused
sustained interference during Mac L2; intermittent application/system work
also exceeded the screen in other campaigns. A dedicated-attestation field
records the user's reservation, not a claim that observed interference passed.

The pinned publish fixture is 100,000 documents × 768 dimensions, all 1,000
queries, SHA-256
`4676911521f13dc6592d102cf3b4fcace85c6b62b3011e9bd57557dfc9c01f2d`.
Competitor parameters: four rounds, k=10, M=16, efConstruction=200,
seed=42, ef=16/32/50/100. All five canonical cosine engines and all six L2
engines, including native sqlite-vec L2, are required.

The comparison binaries include the previously documented
[two-line recording overlay](evidence/2026-11-01-performance/raw-round-recording.patch):
it prints already-collected individual rounds after timing ends, changing no
engine, timer, workload or acceptance check. Candidate source was restored
clean after building. Native binary SHA-256 is
`0762a133290f3bb205aef2ee244e7986581050e3ba5b063a3e94387f3aeef1c0`;
Android binary is
`6f7fa2c6b5f5c5f0627f1f61d255e536c5975cb9766a0f6eb38a8a9c5fc5bc10`.
The fixture, source and prebuilt binaries were rechecked before reuse. Native
campaigns invoked those binaries directly with `--markdown`, preserving the
repository's publish validation without triggering a build in a timing window.
Android uses device JSON followed by the repository host renderer, as documented.

## Interleaved write/search results

Six complete passes, A-B-A-B-A-B, each ran `distance`, `store`, `index` and
`disk`: all 28 rows per pass. Estimates below are medians of three per-pass
Criterion slope point estimates (mean when slope is absent). Every Criterion
sample is retained. The full campaign had **26 load flags in 359 process-phase
samples**, with no AC violation. These are diagnostic numbers, not gate passes.

| Row | Candidate Rust/C++ | Rust change from baseline | C++ change from baseline |
|---|---:|---:|---:|
| store_add/n=10000 | 0.791× | −41.82% | +0.86% |
| disk_build | 1.030× | −15.47% | −1.36% |
| store_search/n=1000 | 1.036× | +0.42% | +0.82% |
| store_search/n=10000 | 0.941× | +0.51% | +0.37% |
| index_search | 1.181× | +3.69% | −0.42% |
| disk_search | 0.978× | −0.08% | −0.24% |

Both write ratios are numerically below RFC 0010's 1.1× limit, but host quality
prevents acceptance. The +3.69% index-search signal exceeded the 3% floor and
both arms' pass spreads (A 1.86%, B 2.44%), prompting focused confirmation.

Eight additional `index_search` runs used the planned order A-B-B-A-B-A-A-B.
Both blocks and the aggregate remain visible, without choosing individual
favorable runs:

| Planned block | Host screen | Rust delta | C++ delta | Ratio-of-ratios delta |
|---|---|---:|---:|---:|
| First ABBA | 2 load flags | +3.26% | −0.88% | +4.18% |
| Second BAAB | All process-phase samples within screen | +1.23% | −4.13% | +5.59% |
| All eight | Nonqualifying | +2.89% | −2.97% | +6.04% |

The clean second block's Rust delta is below 3% and its candidate spread of
3.35%. However, the C++ control shifted by −4.13%; the normalized +5.59% must
not be hidden or interpreted as a proven candidate-specific regression.
The full-run Rust signal is not consistently reproduced, and the overall
no-search-regression gate remains unresolved. A focused engine fix is not
justified by this evidence.

Source inspection also rules out treating C++ as an identical executable
control: both revisions build their own reference engine, and the candidate
adds a full-beam branch to C++ search. At this workload
(N=10,000, ef=50, k=10), that exhaustive branch is not taken. The Rust search
body adds a corresponding full-width guard and changes the widening stop
condition; the benchmark changes its Rust handle representation but retains
the search workload and timed query sweep. These observations identify
potential branch/layout and ABI differences, not a measured causal attribution.
The relevant source diff is retained; no correctness guard was removed to
chase an unstable timing signal.

## Historical fixed-graph signal

The unchanged external native/C API probe loaded the same serialized graph
(SHA-256 `3672206a43d866b598b2abac71babf71181f7d459a2d73687fc8928d389b1cbc`)
in A-normal/B-normal/B-reverse/A-reverse order. All 32 query result IDs and
exact distance bits matched across revisions; the probe also checks native/C
API agreement. Each process retained ten timing rounds per path, with the
first two explicitly marked warmup and eight used in its median. All raw
warmup and timing rows remain available. Each round performs 1,000 sweeps of
32 queries; elapsed time is divided by 32,000 for ns/query.

| Path | Baseline ns/query | Candidate ns/query | Delta | A / B process-median spread |
|---|---:|---:|---:|---:|
| Native | 27,011.82 | 27,362.30 | +1.30% | 1.76% / 1.89% |
| C API | 26,980.55 | 27,518.75 | +1.99% | 1.60% / 2.04% |

All process-phase host samples passed, on AC. Both deltas fall within the
repository's approximately 3% noise floor. The previous approximately 5%
fixed-graph slowdown was **not reproduced in this clean diagnostic**. This
bounded result neither proves the historical observation was only noise nor
passes every search workload. The external probe's source and lockfiles are
retained with November 1 evidence; this is a diagnostic dependency scope,
not validation of every shipping artifact.

## Competitor campaigns and Android

The native Mac cosine and L2 campaigns completed all canonical engines and
four rounds. Original JSON, individual `RAW_ROUNDS` records, rendered tables,
commands and load samples are retained. Both passed the repository renderer
and an independent recomputation of build/search medians, spreads and recall.
Those checks establish report completeness and arithmetic, not timing quality.
Mac cosine had 42 load flags in 397 process-phase samples; L2 had 277 in 423.
Neither supplies qualifying competitor performance evidence.

The existing `vanedb_020_full_api35_arm64` was inspected first. Its November 1
smoke directory contained zero-length files that failed SHA-256 verification,
and only about 5.54 million KiB of guest space remained. No measurement began
there. Its existing September results and other data were preserved. L2 needs
space for approximately 5.15 GB of persisted indices plus temporary SQLite
databases; the existing AVD did not have enough capacity for that workload.

A separate equivalent AVD, **`vanedb_020_acceptance_20261102_api35_arm64`**, uses
the same installed API 35 default ARM64 system image revision 2, four virtual
CPUs, 8192 MiB RAM and a 16 GiB data partition. It runs headless under
Hypervisor.Framework, with GPU disabled and cold boot/no snapshots. Emulator
37.1.11, platform-tools 37.0.1 and NDK 26.1.10909125 are unchanged from setup.
Guest facts report aarch64 / arm64-v8a, API 35, `ro.kernel.qemu=1`, four CPUs
and **4 KiB pages**. These are explicitly emulator results, not physical-device,
native Linux x86-64, or Android 16 KiB-runtime evidence.

The candidate binary, NDK libc++ runtime and pinned fixture were pushed into a
new task directory, synced and verified against host SHA-256 values. The first
new-AVD preflight stopped because the guest sampler treated its absent
benchmark PID file as a command error; its setup record is retained separately.
The sampler was corrected before any timing. Neither setup failure is an
engine regression or a discarded timing run.

Android uses the same host screen, excluding only the controller/sampler,
task-owned emulator tree and active adb command tree. Guest `/proc/stat` and
readable per-process CPU counters are retained approximately every 30 seconds
during execution (five seconds in preflight). Aggregate guest busy ticks minus
the benchmark process's ticks include other guest work and monitoring overhead;
unreadable process rows are counted, and the aggregate still includes their
CPU activity. The guest screen permits at most 50% of one vCPU of aggregate
background activity and at most 50% for any visible individual process.
Each campaign requires three consecutive quiet host/guest preflight samples.
These interval observations do not establish continuous isolation. The raw
field `background_sum` is non-target busy CPU: it also includes interrupt
and filesystem work that the benchmark itself may cause. Its flags must not
be read as proof of competing guest applications. Early L2 flags include
substantial IRQ/softirq and filesystem-worker activity; host-load failures
independently prevent acceptance.

Android cosine completed all five engines and four rounds. Its original JSON
matches the pulled guest checksum, passes the unchanged renderer, and
reconciles to all raw round arrays. **36 host-load flags, zero guest-load
flags and no AC loss** prevent performance qualification. Individual host
spikes include application activity and service startup; none were excluded.

Android L2 also completed all six engines and four rounds. Its pulled JSON
matches the guest checksum, passes the unchanged renderer and reconciles to
all raw round arrays. It recorded **24 host-load flags, 16 non-target guest CPU
flags and no AC loss**. The guest counter's I/O attribution limits are described
above; the independent host failures already prevent acceptance.
