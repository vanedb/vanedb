# 0.1.0 release readiness

Status: **verified, awaiting registry setup**. The active target is the first
**0.1.0** release. The code and its evidence are ready; the three registry
prerequisites below are owner actions and no publication is authorized until
they are done.

**`e3c2635` was an interim checkpoint, not the final candidate — the head has
since moved past it, and no commit is currently designated.** The four
independent assessments (CTO, AI PM, senior engineer, QA) approved at that
revision and QA's earlier BLOCK on "fully test" is lifted; what those
assessments found is not invalidated by the commits since, but the
*designation* is. Re-designating needs a fresh CI run and a fresh set of
publication-disabled rehearsals at the new head, because the recorded
rehearsals predate `99e02a9`, which renamed the npm package.

Designating a candidate before the registry work is done was itself the
mistake. RELEASING.md step 5 puts the packaged-README edit *in the release
commit*, so the final candidate cannot exist until the three registry
prerequisites below are cleared. Until then this record verifies revisions;
it does not nominate one.

The previous record certified `bf797d9`, which is retained further down as
historical evidence. It was superseded for a reason worth keeping visible: the
`sanitize` (AddressSanitizer) and `coverage` jobs did not exist in
`rust-ci.yml` at that revision, so the CI run it cited was a *narrower gate*
than the branch requires. "Passes CI" is a claim about a gate, and the gate is
versioned too — evidence should pin which checks ran, not only that they
passed.

The crates.io bootstrap token was scoped `publish-new` on crate `vanedb` and
revoked immediately. Scoping mattered: the crate now exists, so that scope is
spent and could not have published `0.1.0` even before revocation.

Why a prerelease rather than `0.1.0`: a bootstrap is a hand publish with no
reviewer, no OIDC and no attestation, so the version it spends should not be
the version people install. crates.io burns a version only on a *successful*
publish, so a failed tag costs a retag rather than the number.

The npm rc is the one that earns its keep twice. It proves the trusted
publisher works end to end — `0.1.0` there was a hand publish and carries no
attestation, and npm never frees a used version, so that page cannot be fixed.
Publishing under `next` leaves `latest` on the `0.1.0` a user installs.

### npm is one patch ahead, and needs its own release commit

`@vanedb/wasm@0.1.0` was the manual bootstrap. npm never frees a used version,
so the first attested release there is `0.1.1` while crates.io and PyPI get
`0.1.0`. They realign at the next minor.

`release_identity` requires every version site to agree, so the repo cannot be
`0.1.0` and `0.1.1` at once. That makes this **two release commits**, not one:

1. bump to `0.1.0`, tag `vanedb-crate-v0.1.0` and `vanedb-v0.1.0`
2. bump to `0.1.1`, tag `vanedb-wasm-v0.1.1` only

Both commits pass `release_identity`, because at each one every site agrees.
crates.io and PyPI simply take no `0.1.1` tag. Publishing npm from the first
commit is not possible and not a gap in the tooling: the version there would
read `0.1.0`, which npm refuses.

## Scope and compatibility

Ship the Rust engine and its Python, C and WebAssembly bindings, with runnable
user guides and verification of the advertised platform matrix. Keep the C++
reference and its cross-engine tests working. This candidate does not switch
the production engine during the ongoing language-strategy discussion.

The 0.x API and persistence formats may evolve in minor releases. Existing
format, kind and continuation identifiers must not be reinterpreted; new
encodings require new identifiers while retaining readers for existing files.
Older readers need not accept future formats. Both engines currently preserve
VNDB v1 disk and VNDB v2 graph files across load/save, including graph tombstones.
Future insertions may produce different topology. Legacy-reader and corruption
checks remain required; the version change is not permission to discard them.

Optional Metal compute is a Rust API for explicitly uploaded vectors, not
transparent acceleration of the indexes. CUDA is a required, high-priority
[follow-up after the initial release](../ROADMAP.md), with no assigned version
or date. Mobile acceptance uses simulators/emulators; physical-device acceptance
remains a follow-up. Neither CUDA nor physical-device success is claimed here.
